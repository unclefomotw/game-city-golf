# 實作決策紀錄（ADR）

記錄重要的實作取捨。每筆包含背景、考慮過的選項、決定、理由，並引用相關的 spec 條目。
決策被推翻時不要刪除舊紀錄：把狀態改為「已被 ADR-xxx 取代」，再新增一筆。

## ADR-001：使用 TypeScript + Vite + Three.js

- 狀態：採用
- 日期：2026-10-16
- 相關 spec：PLT-1, PLT-3, DES-1, VIS-1

**背景**：需要一個能在網頁上執行、手機桌機都能跑的 3D 渲染方案。程式主要由 AI agent 撰寫，使用者不熟 React。

**選項**：
- Three.js：輕量，生態系與範例最多，code-first。
- Babylon.js：功能齊全（內建物理、GUI、inspector），但對這個專案來說太重。
- React Three Fiber：宣告式寫法，但多一層抽象，使用者也不熟 React。
- Godot Web 匯出：有關卡編輯器，但匯出檔案大、載入慢。這個專案的關卡是程序生成（LVL-1），用不到編輯器。

**決定**：TypeScript + Vite + 純 Three.js（命令式）。

**理由**：場景只由方塊構成，Three.js 就夠用；code-first 適合 agent 撰寫與維護；Vite 建出來是靜態檔，部署簡單。

## ADR-002：自寫簡化物理，不使用物理引擎

- 狀態：採用
- 日期：2026-10-16
- 相關 spec：PLAY-3, VIS-2, DES-4, DES-6

**背景**：spec 明確要求不需要擬真物理（VIS-2），碎塊只是視覺效果（DES-6）。真正需要碰撞的只有「球 vs 地面與建築」。

**選項**：
- 物理引擎（Rapier、Havok、cannon-es）：功能完整，但手感難調，結果也不容易保證可預期。
- 自寫：拋物線、旋轉偏移、彈跳衰減，加上球對格子的碰撞查詢。

**決定**：自寫。

**理由**：程式碼少、手感完全可控、固定時間步長下結果可重現，符合 PLAY-3。建築用格子表示（ADR-003），碰撞查詢本來就很簡單。如果日後需求改成「碎塊會影響球」，再重新評估要不要引入物理引擎。

## ADR-003：建築以 3D 格子（voxel）表示

- 狀態：採用；渲染方式由 ADR-019 修訂（每種材質一個 `InstancedMesh`）
- 日期：2026-10-16
- 相關 spec：DES-2, DES-3, DES-4, DES-5, VIS-1

**背景**：建築要能被球挖出洞（DES-3），而且挖完之後的形狀要影響球路（DES-4）。

**選項**：
- 每棟建築是一個完整的長方體，破壞時整棟換成碎片：做不出「挖掉一部分」的效果。
- 預先把建築切成數塊，破壞時移除整塊：粒度太粗，洞的位置不由撞擊點決定。
- 3D 格子：破壞就是把格子刪掉，碰撞就是查詢格子是否被佔用。

**決定**：3D 格子，用 `InstancedMesh` 渲染。

**理由**：刪除格子同時解決「渲染變化」和「碰撞變化」，天然符合粗糙的方塊風格（VIS-1）。格子大小是調整效能和視覺粒度的主要參數。

## ADR-004：UI 用原生 DOM + CSS，輸入用 Pointer Events

- 狀態：採用
- 日期：2026-10-16
- 相關 spec：PLT-3, UI-1, UI-2, UI-3

**背景**：需要正方形主畫面，加上會隨螢幕方向切換位置的控制面板；滑鼠與觸控都要支援。

**決定**：控制面板用 DOM + CSS 實作（不使用 UI 框架），版面以 `aspect-ratio` 和 `@media (orientation)` 處理；輸入統一使用 Pointer Events。

**理由**：UI 元件不多，不需要框架。Pointer Events 讓滑鼠和觸控共用同一套程式，減少兩套行為不一致的風險。

## ADR-005：部署到 GitHub Pages

- 狀態：擱置（2026-10-17，使用者目前不打算公開部署，已移除 workflow；需要時再恢復）
- 日期：2026-10-16
- 相關 spec：PLT-1, ACC-1

**背景**：使用者要在手機和桌機上實際遊玩驗收，需要一個固定網址。

**決定**：用 GitHub Actions 在推送到 main 後自動建置並部署到 GitHub Pages。

**理由**：免費，不需要額外帳號，而且和 repo 綁在一起。開發期間另外可以用 `vite --host` 在區網內直接用手機測試。

## ADR-006：球的運動採用類 Magnus 旋轉模型，參數可即時調整

- 狀態：採用（暫定，待試玩驗證）
- 日期：2026-10-16
- 相關 spec：PLAY-3, SHOT-3, SHOT-4, VIS-2

**背景**：左右旋和上下旋都要支援（SHOT-3）。使用者還不確定哪種旋轉行為比較好，希望透過實際遊玩反覆驗證（SHOT-4）。

**選項**：
- 固定側向加速度，隨時間衰減：最簡單，但與球速無關，球幾乎停下時還在彎，看起來不自然。
- 類 Magnus 力 `k · (ω × v)`，旋轉隨時間衰減：一個公式同時涵蓋左右旋（側彎）與上下旋（升力或下壓），效應自然隨速度與方向變化。
- 擬真的空氣動力模型：參數多又難調，也不符合 VIS-2。

**決定**：採用類 Magnus 力加上旋轉衰減，空氣阻力用線性模型。各力項寫成可以開關、可以替換的獨立函式。所有參數集中在設定物件，`?debug` 模式下用 lil-gui 即時調整。

**理由**：公式少、行為直覺，而且在固定時間步長下結果確定，預覽軌跡會和實際結果一致（PLAY-3）。即時調參讓「試玩→調整」的循環縮到最短。如果試玩後覺得不好控制，可以換成較簡單的模型，不影響其他模組。

## ADR-007：視角分成擊球模式與靈魂出竅模式；手機用畫面外的虛擬搖桿

- 狀態：採用（暫定，待試玩驗證）
- 日期：2026-10-16
- 相關 spec：CAM-1, CAM-2, UI-2, UI-3

**背景**：使用者想要「靈魂出竅」的自由視角（CAM-1）。桌機有 WASD + 滑鼠轉視角的慣例可以參考，手機需要另外找方案。

**選項（手機）**：
- 雙虛擬搖桿（左手移動、右手轉向）：手機 3D 遊戲最常見的配置，玩家熟悉，但搖桿疊在畫面上會擋住場景。
- 地圖式手勢（單指平移、雙指縮放與旋轉）：像地圖 App 或城市建造遊戲一樣直覺，但很難表達「飛進建築的洞裡看」這類 3D 自由移動。
- 點擊目的地飛過去：簡單，但無法細微控制。

**決定**：在擊球模式用繞球旋轉的相機。在靈魂出竅模式，手機把移動用的虛擬搖桿和上下按鈕放在**正方形以外的控制區**，正方形畫面內單指拖曳轉視角、雙指捏合前進或後退；桌機用 WASD + Q/E + 滑鼠。兩種模式都有「回到球」按鈕。

**理由**：UI-2 本來就在正方形外保留了控制區，搖桿放在那裡就不會擋到場景，同時保留雙搖桿的熟悉度。相機控制寫成可以替換的模組，試玩後如果想改成地圖式手勢，替換成本很低。

## ADR-008：彈弓式拖曳決定水平方向與力道，仰角用滑桿

- 狀態：已被 ADR-013 取代
- 日期：2026-10-17
- 相關 spec：SHOT-1, SHOT-2, PLAY-2

**背景**：擊球需要三個值：水平方向、仰角、力道（SHOT-1）。螢幕上的一次拖曳只有兩個自由度。

**選項**：
- 拖曳同時決定水平方向與仰角，力道另外設定：在透視畫面上很難判斷「往上拖」代表仰角還是往遠處。
- 拖曳決定水平方向與力道，仰角另外設定：和 Angry Birds 這類彈弓操作的直覺一致，拖越長越用力。
- 全部用滑桿：精確，但缺乏手感。

**決定**：拖曳（從球附近開始，反向發射）決定水平方向與力道，仰角用面板上的滑桿。另外提供力道滑桿和方向微調鈕，方便精確調整。設定好之後按「擊球」才發射，不在放開時立即發射。

**理由**：每個值都有一個明確的控制方式，加上 3D 箭頭、地面投影、仰角弧線和預覽軌跡，玩家發射前就能看清楚 3D 方向（SHOT-2）。分開「設定」與「發射」，讓滑鼠和觸控都能慢慢調整後再出手。

## ADR-009：用 Biome 做 formatter 與 linter

- 狀態：採用
- 日期：2026-10-17
- 相關 spec：無（開發流程）

**背景**：程式主要由不同的 coding agent 在不同 session 撰寫，排版習慣容易不一致，讓 diff 難以檢查。`tsc` 已開啟 `strict` 與未使用變數檢查，型別層面的問題大多已涵蓋。

**選項**：
- ESLint + typescript-eslint + Prettier：規則最完整，能做需要型別資訊的檢查（例如 `no-floating-promises`），但要維護三套工具與設定。
- Biome：單一工具同時做格式化、lint、import 排序，零依賴、速度快；需要型別資訊的規則較少。
- 不加：只靠 `tsc` 和 AGENTS.md 的文字約定。

**決定**：使用 Biome，採推薦規則。`lineWidth` 設為 120、單引號，貼近既有程式碼，減少第一次格式化的改動量。關閉 `style/noNonNullAssertion`：DOM 查詢與 `getContext('2d')` 的 `!` 是這個專案的慣用寫法，逐一改寫只會增加雜訊。`npm run check` 串起 Biome、`tsc`、Vitest，AGENTS.md 要求交付前必須通過。

**理由**：程式幾乎沒有非同步流程，用不太到需要型別資訊的 lint 規則，一個工具就夠了。把規範寫成可執行的檢查，比寫在文件裡更不容易被 agent 漏掉。日後如果需要更嚴格的型別規則，再評估改用或加上 typescript-eslint。

## ADR-010：開發者測試場景只在開發模式提供

- 狀態：採用
- 日期：2026-10-17
- 相關 spec：SHOT-2, SHOT-4, PLAY-3, ACC-1；與第 5 節「手工關卡」非目標的關係見理由

**背景**：使用者在試玩調整擊球手感（SHOT-2、SHOT-4）時，需要可以重複開啟、沒有干擾的固定場景。隨機城市每張都不同，建築也會擋住視線、改變球路，不適合觀察「力道與距離」這類基本手感。需求是：場景預先定義、開發者容易挑選，而且最好能擋住一般玩家，至少不能在正常玩法中隨機到。

**選項**：
- 保留特定 seed 當作測試場景：不需要新機制，但 seed 是隨機城市的一部分，玩家可能抽到，而且無法做出「沒有建築」這種生成器做不出的場景。
- 網址參數 `?scene=<id>`，任何環境都能開：最簡單，但玩家只要知道網址就能進入。
- 網址參數 `?scene=<id>`，只在開發模式有效：靠 Vite 的 `import.meta.env.DEV` 判斷，正式 build 會連同場景程式碼一起移除。

**決定**：第三個選項。場景定義在 `world/testScenes.ts`，各自產生一個 `Level`，與隨機城市共用同一套遊戲、物理和渲染。開發模式下面板會出現下拉選單切換場景。

**理由**：正式 build 根本不含測試場景，比任何隱藏網址都可靠，玩家既無法隨機到，也無法手動打開。開發者原本就用 `npm run dev` 透過區網在桌機與手機試玩（ADR-005），所以這個限制不影響使用。測試場景是開發工具，不會出現在玩家的遊戲裡，因此不違反 spec 第 5 節「不做手工關卡」的非目標，也不改變 LVL-1（玩家玩到的關卡都由程式生成）。如果之後需要在部署後的環境使用測試場景，只要把判斷條件改成 build 時的環境變數即可。

## ADR-011：靈魂出竅的前進方向跟著視線的仰角；保留升降按鍵

- 狀態：採用（暫定，待試玩驗證）
- 日期：2026-10-17
- 相關 spec：CAM-1, UI-3

**背景**：原本靈魂出竅模式的 WASD／搖桿只在水平面移動，改變高度只能靠 Q/E、升降按鈕或捏合。玩家往下看再按前進時高度不變，感覺像被鎖在同一個高度。

**選項**：
- 維持水平移動，只靠升降按鍵改變高度（類似 Minecraft 創造模式）。
- 前進沿視線方向，並拿掉升降按鍵：控制最精簡，但無法在維持視線的情況下升降，也無法完全垂直起降（仰角上限約 ±86°）。
- 前進沿視線方向，同時保留升降按鍵：多數自由飛行相機的做法。

**決定**：第三個選項。前進／後退（W/S、搖桿上下）沿著含仰角的視線方向；左右平移維持水平；Q/E 與手機的升降按鈕維持純垂直移動。

**理由**：往想去的地方看再前進最直覺，符合 CAM-1「自由移動、自由轉向」。升降按鍵放在正方形外的控制區，不擋畫面，成本很低，而且在「盯著某棟樓往上飛越屋頂」這類情況仍然需要。如果試玩後發現手機控制區太擠，或升降按鈕很少用到，可以再拿掉。

## ADR-012：操作提示依玩家實際使用的輸入方式切換

- 狀態：採用
- 日期：2026-10-17
- 相關 spec：PLT-3, UI-3, CAM-1

**背景**：操作提示同時寫了鍵盤滑鼠和手機兩套操作，內容很長，而且有一半跟玩家無關。

**選項**：
- 依主要指標裝置判斷（`(pointer: coarse)`）：觸控筆電、接鍵盤的 iPad 這類混合裝置會判斷錯。
- 依有沒有觸控能力判斷（`maxTouchPoints`、`any-pointer`）：有觸控螢幕的筆電會被當成手機。
- 依 User-Agent 判斷：不可靠，iPadOS Safari 會自稱是 Mac。
- 先用 `(pointer: coarse)` 猜，再跟著最後一次實際輸入切換：`pointerdown` 的 `pointerType` 是 mouse 就切到滑鼠鍵盤，是 touch／pen 就切到觸控；按任何鍵也切到滑鼠鍵盤。

**決定**：最後一個選項。只改提示文字，搖桿、升降按鈕等控制項仍然不分裝置都顯示。猜測結果不存到 localStorage。

**理由**：初始猜測對大部分裝置是正確的，混合裝置在第一次操作後也會修正。因為控制項不隱藏，就算猜錯也只是提示文字不對，不會讓玩家無法操作（UI-3）。存到 localStorage 只能改善「混合裝置重新整理後、第一次操作前」這一小段時間，還可能沿用上次已經不成立的狀態，所以不做。如果之後要依裝置隱藏控制項，可以沿用同一個判斷。

## ADR-013：用面板上的方向搖桿以速率控制方向與仰角；場景拖曳只轉視角

- 狀態：採用（2026-10-17 使用者試玩後選定）；取代 ADR-008
- 日期：2026-10-17
- 相關 spec：SHOT-1, SHOT-2, SHOT-5, PLAY-2, UI-2, UI-3, PLT-3

**背景**：ADR-008 的彈弓式拖曳和「拖曳空白處轉視角」共用同一個畫面，從球附近開始拖還是從空白處開始拖，行為完全不同，容易誤觸；仰角又要另外到滑桿調整，方向微調則靠 ◀ ▶。使用者想試另一種操作：所有擊球設定都放在正方形外的控制區，場景只用來看。

**選項**：
- 位置控制的搖桿（偏移直接對應角度）：放開就會彈回，角度會跟著歸零，必須一直按住，不適合「慢慢調好再擊球」。
- 速率控制的搖桿（偏移對應轉動速度）：放開後角度停住；推一點點可以微調，推到底可以快速轉向。一支搖桿同時涵蓋水平方向與仰角。
- 保留滑桿與 ◀ ▶，只拿掉彈弓：控制項多、操作分散。
- 兩段式（與本方案同時試玩，未採用）：先用彈弓式拖曳決定水平方向與仰角，放開後場景上出現 0→100 來回震盪的力量條，按擊球鈕決定力道。實作保留在 `feature/ux-two-stage` 分支（commit `8d04205`），之後若要重新評估可以從那裡取回。

**決定**：
- 速率控制的方向搖桿，左右轉水平方向、上下調仰角。符號：往右推方向往右轉；**往上推仰角變大**（像把準星往上抬，而不是飛行模擬的「推桿低頭」）。
- 偏移先扣掉中心死區，再套用 `t^n` 反應曲線（預設 n = 2），中心附近轉得慢、方便微調。轉速、死區、曲線、方向鍵力度都放在 `config.aim`，可以在 `?debug` 面板調整。
- 桌機的方向鍵等同把搖桿推到固定偏移量。方向鍵沒有被其他操作使用，不會和靈魂出竅的 WASD/QE 衝突。
- 後來使用者要求擊球模式也能用 WASD 瞄準（W/S 仰角、A/D 水平方向）。瞄準只在擊球模式讀取，擊球模式的繞球相機也不使用移動輸入，所以同一組按鍵依模式分工，不會衝突。
- 移除仰角滑桿、方向 ◀ ▶ 與彈弓拖曳。力道保留水平滑桿，但縮短，和搖桿、旋轉球面排成同一列。
- 3D 箭頭、地面投影、仰角弧線與預覽軌跡（SHOT-5）不變，每一幀依目前的角度更新，所以推搖桿時會即時轉動。

**理由**：一支搖桿就能調整兩個角度，滑鼠和觸控的操作方式完全相同（UI-3、PLT-3），而且放在正方形外，不會擋到場景（UI-2）。場景拖曳只剩下轉視角，不會再誤觸擊球設定。3D 視覺回饋沒有改，玩家發射前仍然看得清楚 3D 方向（SHOT-2）。

**已知取捨**：速率控制要「等它轉過去」，大角度轉向比彈弓慢；轉速與反應曲線需要試玩調整。橫向面板只有 280px 寬時，力道滑桿只有約 86px，精確度比原本低。

## ADR-014：建築延伸到場地邊界；起點固定在角落並保留無建築範圍

- 狀態：生成方式已被 ADR-016 取代；保留「起點固定在角落、周圍淨空」的決定（淨空改為 5 格）
- 日期：2026-10-17
- 相關 spec：LVL-1, LVL-3, FLD-1

**背景**：原本的生成在場地四周留了 3 格不蓋建築的邊，玩家可以沿著空的邊界一路打到終點，城市形同虛設。起點隨機放在四個角落之一，周圍沒有明確的淨空保證，最近的建築面只離起點中心 1.5 格。使用者要求：建築可以貼到邊界、起點固定在 (1.5, 1.5)、起點周圍約 2 格內不能有建築，終點規則不變。

**選項**：
- 起點淨空用「挖掉」範圍內的方塊：建築會被咬掉一角，形狀零碎。
- 裁切地塊：和淨空範圍重疊的地塊裁成不重疊的最大長方形，太小就不蓋。建築維持長方體（VIS-1）。

**決定**：
- 切街區時不再保留邊距；最後一塊街區延伸到邊界，吃掉末端剩下的道路或太窄的零頭（街區最寬可能到約 22 格）。
- 貼邊界的地塊那一側不內縮。
- 起點固定在 `TEE = (1.5, 1.5)`，以 `TEE_CLEARANCE = 2` 定義每軸的淨空範圍（換算成格子是 0 ~ 3），用裁切地塊的方式排除建築。
- 終點規則不變。

**理由**：玩家沒有空邊界可以繞，路線規劃要面對城市。裁切讓建築維持長方體，淨空範圍是明確常數，有單元測試檢查。起點固定在角落後，終點一定在對角那一側，距離比原本更穩定。

**已知取捨**：每張地圖的起點方位都一樣。道路仍然會在邊界形成死巷，空地塊和地塊之間的縫也會露出邊牆，大約四成的邊界格是空的，但已經沒有連續的邊界通道。

## ADR-015：路網只開放部分路段，限制直路長度

- 狀態：已被 ADR-016 取代（試做後未採用，沒有發布）
- 日期：2026-10-17
- 相關 spec：LVL-1, LVL-3, DES-1
- 修訂：ADR-014（起點淨空由 2 格擴大為 5 格；淨空區延伸成通道接上路網）

**背景**：街區是兩個軸各自切出來再交叉組合的，所以每條道路都從邊界的一端直通到另一端，形成棋盤狀的長直路。使用者覺得太無聊：雖然以城市為比喻，但不需要很長、很暢通的路。使用者同時要求把起點淨空擴大到 5 格。

**選項**：
- 遞迴切割（BSP）：子區塊的路會在父區塊的路上形成 T 字路口，但第一刀的路仍然貫穿整個場地。
- 在棋盤路網上把部分路段封起來：沿用現有的街區切法，只決定哪些路段開放。可以直接限制同一條線上連續開放的段數，也容易確保連通。
- 完全不用街區的迷宮式生成：變動太大，建築也不容易維持長方體。

**決定**：
- 把路口看成格點，用隨機深度優先走出連通所有路口的樹，再以 `LOOP_CHANCE`（10%）補幾段迴圈。開放任何一段時，同一條線上連續開放的段數都不能超過 `MAX_ROAD_RUN`（2）。
- 碰到邊界的末端路段一律封閉，只開放起點那一段。
- 封閉的路段與路口蓋一棟建築，並往兩側各多佔 1 格。這是因為一開始讓相鄰街區併入封閉路段時，地塊內縮留下的 1 格縫會沿著原本的路線接起來，直線空地仍然長達 64 ~ 72 格。
- 起點淨空 5 格（地格 0 ~ 6），並沿邊牆延伸到起點那一段末端路段。延伸方向隨機。
- 終點只從旁邊有開放路段的遠方街區挑，確保地面可以走到。

**理由**：只要改動「哪些路段開放」，就能把直路長度變成一個可調的常數，路網仍然連通，所以 LVL-3 的地面通道檢查不必改。建築仍然是長方體（VIS-1）。

**量測**（seed 0 ~ 1999）：
- 沒有生成失敗。
- 直線道路最長約 40 格，有測試檢查。
- 2 格寬以上的直線空地，中位數 36 格、第 90 百分位 38 格。
- 邊界格約 19% 是空的。

**已知取捨**：
- 偶爾（約 1%）同一欄街區裡地塊之間的縫剛好對齊，再加上空地或終點廣場，會出現 50 格以上、1 ~ 2 格寬的直線窄巷。那些是建築間的縫，不是道路。
- 開放的路段比較少，有些區域完全沒有道路，只能從建築上方飛過或把建築打穿。
- 想讓路更短，可以調整 `MAX_ROAD_RUN`。但設成 1 會讓每個路口最多只有兩條路，路網退化成一條蜿蜒的單線。

## ADR-016：散放可重疊的長方形建築，限制直線空地長度

- 狀態：採用
- 日期：2026-10-17
- 相關 spec：LVL-1, LVL-3, DES-1, VIS-1
- 取代：ADR-015；ADR-014 的街區切法

**背景**：ADR-015 在棋盤路網上封掉部分路段，直路確實變短了，但建築覆蓋率高達約 69%（最早的版本約 33%），使用者覺得 XZ 平面太擁擠。使用者重新定義問題：在平面上放若干長方形，長方形可以重疊；沒被涵蓋的面積不能太小；而且不能有任何直的路從邊界的一端通到另一端。

**選項**：
- 繼續調整路網：只要以「路」為單位，空地就只存在於路上。要降低密度，就得開更多路，直路又會變長，兩個目標互相衝突。
- 散放長方形，再修補過長的直線空地：密度和直線長度可以各自用一個參數控制。空地不再只是路，而是不規則的開放區域。

**決定**：
- 先隨機散放長方形到覆蓋率 `COVERAGE`（30%）。接著把每一列、每一欄中超過 `MAX_OPEN_RUN`（36 格）的直線空地，在它的中段用一個小長方形擋住，重複到沒有為止；修補用的長方形一定要蓋到選中的那一格。
- 「直的路」只看沿 x、z 軸的直線，不看斜線。`MAX_OPEN_RUN` 比場地邊長小，所以使用者要求的「不能從邊界通到邊界」一定成立。設成 36（場地的一半），是因為只擋住「整列全空」的話，最長的直線空地中位數仍有 60 格，和貫穿差不多。
- 起點與終點周圍是保留區，長方形會被裁開。終點不再綁定街區，改成在遠方隨機挑一個點，再清出一塊廣場。
- 沒有特別處理起點與路網的連接。LVL-3 的地面通道檢查沒有改，失敗就在同一個亂數序列裡重試。

**理由**：空地比例和直線長度各自是一個可調參數，試玩時可以分開調整。長方形允許重疊，所以建築外形比較自然，也仍然是由長方體組成（VIS-1）。

**量測**（seed 0 ~ 1999）：
- 沒有生成失敗。
- 覆蓋率平均約 40%，最多約 47%。
- 直線空地最長 36 格，有測試檢查。
- 終點離起點 70 ~ 94 格。

**參數取捨**：`MAX_OPEN_RUN` 設成 30 時，覆蓋率會升到約 44%。如果 `COVERAGE` 不變、`MAX_OPEN_RUN` 調得更小，修補會補進更多小建築，空地就會變少。

**已知取捨**：
- 沒有「街道」的城市感，比較像散落的建築群。
- 斜向的長直線沒有限制。

## ADR-017：擊球模式的相機依俯視角度調整球在畫面上的高度

- 狀態：採用
- 日期：2026-10-18
- 相關 spec：CAM-2、SHOT-5

**背景**：擊球模式的相機一直對準球。平視時球在畫面正中間，下半部幾乎都是地面，前方的建築和天空只佔一半。使用者提議：平視時讓球在畫面偏下，越往下俯視越接近中心，正上方俯瞰時在正中間。

**選項**：
- 把相機往上轉一點（看向球的上方）：只改相機朝向，投影矩陣不變，點擊、射線等換算都不受影響。缺點是平視時畫面有輕微仰角，建築的垂直線會稍微往上收斂。
- 鏡頭位移（偏移投影矩陣）：垂直線保持垂直，但要自己維護投影矩陣，處理視窗縮放和反矩陣。

**決定**：採用往上轉。球在畫面上的目標位置（NDC，-1 是底、0 是中心）為 `-levelBallScreenOffset × cos(俯角)`，俯角限制在 0 ~ 90°；依視野角度換算成仰角，在 `lookAt` 之後繞相機自身的 X 軸轉。用的是實際顯示的俯角（建築擋住時自動抬高後的值），所以自動抬高時球也會跟著往中心移。

**理由**：實作最單純，副作用最少；目前的視野角度下，仰角最多約 13°，垂直線收斂不明顯。`levelBallScreenOffset` 預設 0.45，可以在 `?debug` 面板調整。

**已知取捨**：球飛行時也套用同樣的構圖。

## ADR-018：預覽軌跡在第一次撞擊截斷，並依相機距離漸淡

- 狀態：採用
- 日期：2026-10-18
- 相關 spec：SHOT-5、SHOT-2

**背景**：使用者要求預覽軌跡碰到任何東西就不再往下畫，讓玩家不能靠預覽判斷反彈（spec v0.3 修改了 SHOT-5）；另外希望軌跡的點有深淺，離相機越遠越淺，增加 3D 感。

**截斷的判斷**：沿用物理模擬的事件。`previewPath` 在某一步產生 `bounce` 或 `destroy` 事件時停止，且不收錄該步的位置，所以最後一點停在撞擊前（最多差一個時間步）。
- 球在地面上滾動是「接觸」但不是反彈，不會截斷，所以仰角 0 的推桿仍會顯示一段滾動路徑。
- 撞擊速度低於 `physics.rollThreshold`（2）的碰撞不算反彈，不會截斷。0.6 秒的預覽內幾乎不會發生，先不處理。
- 往下打進地面的球第一步就反彈，此時只剩箭頭，沒有預覽點。

**深淺的做法**：選項有 (a) 每點改顏色、(b) 每點改透明度。白點畫在建築和天空上，改顏色深淺在不同背景上不一致，所以採用 (b)：在 `InstancedMesh` 上加一個每實例的透明度屬性，用 `onBeforeCompile` 乘進 `MeshBasicMaterial` 的透明度。透明度依該點與相機的距離，在本次軌跡的最近與最遠點之間線性內插，距離差至少以 `preview.depthFadeSpan` 計。

**已知取捨**：漸層是相對於軌跡本身的遠近，不是絕對距離；從正後方看時，軌跡前端會明顯變淡。

## ADR-019：建築材質用像素風貼圖呈現，物理與計分依材質查表

- 狀態：採用；配色方式（「材質主要靠底色分辨」與碎塊的代表色）已被 ADR-020 取代
- 日期：2026-10-18
- 相關 spec：VIS-1、VIS-3、DES-2、DES-3、DES-4、DES-7、DES-8、SHOT-5、PLAY-3
- 修訂：ADR-003（建築由一個 `InstancedMesh` 改為每種材質一個）

**背景**：使用者想讓建築看起來有材質（鐵、石頭、磚頭、木頭、玻璃），而且材質要影響彈性與脆弱度（spec v0.4 新增 VIS-3、DES-8）。暫定一棟建築一種材質，也就是關卡生成裡的每個長方形一種材質。破壞分數依材質加權，使用者指定 1、2、3、5、8 分（玻璃→鐵）。

**畫面的選項**：
- (a) 像素風貼圖：開場時用 canvas 畫 16×16 的小圖，每個方塊面貼一張。
- (b) 在 shader 裡依位置算出花紋：花紋可以跨格連續，但要寫和調整 GLSL。
- (c) PBR、法線貼圖、真透明的玻璃：寫實，但手機負擔重，也違反 DES-1 的「非擬真」。另外，透明方塊放在同一個 instanced mesh 裡會有排序問題。

**決定（畫面）**：採用 (a)，由使用者選定。
- 每種材質一個 `InstancedMesh`，各自配一個材質物件，不改 shader。繪製呼叫從 1 次變成 5 次（陰影也一樣），手機上也感覺不到差別。
- 貼圖在 `render/materialTextures.ts` 用程式畫出來，不需要圖檔。放大時用 `NearestFilter` 保持像素感，縮小時用 mipmap，避免遠處的牆閃爍。
- 材質主要靠**底色**分辨（磚紅、木褐、暖米色的石頭、冷藍灰的鐵、亮藍的玻璃），紋理是第二層線索，讓遠處和手機小螢幕上也看得出來（VIS-3）。
- 玻璃和鐵用 `MeshPhongMaterial` 加一點高光，其他用 `MeshLambertMaterial`。玻璃是**不透明的假玻璃**。
- 原本「隔行變暗的窗戶」拿掉，改由貼圖呈現質感。`instanceColor` 只保留些微明暗變化，讓相鄰建築和相鄰方塊有區別。
- 碎塊太小、又會縮小，貼圖看不出來，所以用各材質的代表色（`MATERIAL_COLORS`），維持一個 mesh。

**決定（物理）**：
- 格子仍然只存「建築 id + 1」，材質從建築查詢（`world/materials.ts` 的 `materialLookup`）。`World` 多一個 `materialOf`；沒有提供時一律當成磚頭，也就是材質出現以前的手感，所以手寫的測試格子不用改。
- 反彈：碰撞時取**陷入最深的那一格**的材質，用它的 `restitution` 與 `bounceFriction`。
- 挖洞：門檻改成逐格判斷。每一格只有在撞擊速度超過該格材質的 `minSpeed` 時才會被打壞；半徑是 `min(maxRadius, 速度 × radiusPerSpeed) × radiusScale`。所以同一次撞擊可以打碎玻璃，卻停在後面的鐵牆前。被撞到的那一格只要超過門檻就一定會碎，所以 `minSpeed` 真的就是「開始會壞的速度」。
- `radiusScale` 乘在 `maxRadius` 的上限之後。如果先乘再套上限，全力擊球時玻璃和木頭會挖出一樣大的洞，脆弱度就看不出差別。
- 穿透時的減速改成逐格乘上該格材質的 `speedKeptPerCell`。
- 撞擊速度低於所有材質中最低的 `minSpeed` 時直接略過挖洞，例如在屋頂上滾動時。
- 預覽（SHOT-5）跑同一套模擬，也帶入 `materialOf`，所以預覽和實際結果一致。結果仍然可以重現（PLAY-3）。

**初始參數**（`config.materials`，可以在 `?debug` 面板的「材質」分組即時調整）：

| 材質 | restitution | bounceFriction | minSpeed | radiusScale | speedKeptPerCell |
|---|---|---|---|---|---|
| 玻璃 | 0.15 | 0.75 | 2 | 1.6 | 0.998 |
| 木頭 | 0.2 | 0.6 | 3 | 1.25 | 0.99 |
| 磚頭 | 0.35 | 0.7 | 5 | 1 | 0.985 |
| 石頭 | 0.5 | 0.75 | 12 | 0.75 | 0.97 |
| 鐵 | 0.7 | 0.85 | 25 | 0.5 | 0.95 |

磚頭沿用材質出現以前的建築參數。滿力道的初速是 42，所以鐵只有接近全力的正面撞擊才打得壞。

**參數調整（2026-10-18）**：依使用者要求，滿力道初速 `maxLaunchSpeed` 從 42 降到 36（含空氣阻力，最遠飛行距離約從 77 格降到約 59 格），鐵的 `minSpeed` 從 25 降到 21、`speedKeptPerCell` 從 0.95 降到 0.9。以 36 的速度垂直正面撞鐵牆（不計阻力）模擬：第一下依撞擊點在格子上的位置打掉 4～6 格，與門檻無關；打穿後每打掉一格速度乘 0.9，撞到第二層時只剩約 19～24，所以鐵最多再被打穿一層，總共 5～8 格。原本 0.95 時球可以在鐵裡鑽出很深的隧道，不符合「鐵極堅固」（DES-8）。同時依使用者要求調整其他材質：石頭 `minSpeed` 12 → 15、`speedKeptPerCell` 0.97 → 0.965，磚頭 `minSpeed` 5 → 7，木頭 `minSpeed` 3 → 4。同樣的模擬下，石頭總共打掉 25～28 格、鑽 4～8 層；木頭和磚頭穿進去後的速度仍高於門檻，會一路鑽出很深的隧道。

已知取捨：打穿後的減速是依「這一下打掉的格數」計算，包含不在球路上的格子，所以第一下打掉越多格，球反而鑽得越淺（例如打在格子交界線上比打在格子交角更難打穿第二層）。使用者決定暫時維持這個規則。

**決定（關卡生成）**：每個長方形用一次亂數抽材質，取代原本抽顏色，所以同一個 seed 的建築形狀和以前一樣。高樓（20% 機率）偏向玻璃、鐵、石頭，矮樓偏向木頭、磚頭（`MATERIAL_WEIGHTS`）。

**決定（計分）**：`game/scoring.ts` 用寫死的權重 `MATERIAL_SCORE`（玻璃 1、木頭 2、磚頭 3、石頭 5、鐵 8），由使用者指定，不從物理參數推算。畫面上的「破壞 +N」也改成顯示分數。

**已知取捨**：
- 屋頂和牆面用同一張貼圖。
- 兩個長方形重疊時，重疊的格子屬於後放的那棟，所以看起來是一棟建築有兩種材質（和以前的顏色分法一樣，使用者已確認）。
- 每格的貼圖都一樣，大面牆會看出重複的圖樣。如果試玩覺得太明顯，可以改成在 shader 裡算花紋（選項 b）。

## ADR-020：材質與顏色拆開：灰階紋理表現材質，每棟建築另外上漆

- 狀態：採用
- 日期：2026-10-18
- 相關 spec：VIS-1、VIS-3、DES-8
- 取代：ADR-019 的配色方式

**背景**：ADR-019 讓每種材質只有一種寫實的顏色，結果全城只剩五種顏色：玻璃和鐵都是藍灰，木頭、磚頭、石頭都是暖褐色，失去了材質出現以前隨機十種顏色的繽紛感。使用者希望恢復繽紛，同時材質仍然分得出來。

**選項**：
- (a) 把五種代表色調得更鮮明、差異更大：容易辨識，但全城還是只有五種顏色。
- (b) 回到全部隨機的顏色：最繽紛，但同色的玻璃和鐵很難分辨。
- (c) 材質和顏色拆開：紋理負責材質，每棟建築從**該材質自己的色盤**抽一個漆色。

**決定**：採用 (c)。
- 貼圖改成接近灰階（`render/materialTextures.ts`），只畫結構。漆色透過 `instanceColor` 乘在貼圖上。
- 為了在灰階下也分得出來，五種紋理的差異刻意做大：磚是細小錯縫的長方形磚（7×3 的磚加深色灰縫，每塊磚深淺差異大）、石頭是大小不一的不規則石塊拼成的亂石牆（加權 Voronoi，在貼圖邊緣循環以便無縫拼接），有深色石縫和明顯斑點、木頭是豎立、寬度不一的木板加深色接縫和直向木紋，像一排豎起來的木柱；鐵是一整塊素色鐵板，有細細的深色邊框，四個角落各有一顆鉚釘、玻璃是一整片由亮到暗的窗格，加上白色反光和深色窗框。玻璃的高光比鐵強。
- 紋理的亮部接近白色，避免漆色被壓暗。
- 色盤在 `world/levelGen.ts` 的 `MATERIAL_PALETTES`，每種材質 4～5 種顏色。例如鐵是低飽和、偏暗的貨櫃紅、藍、綠、橘和鋼灰；木頭是深木色、薄荷綠、鵝黃、粉紅和原木色；玻璃是偏亮的淡青、淡綠、淡金、淡紫、淡藍。
- 漆色只影響外觀，不影響玩法。它用另一條由 seed 衍生的亂數序列抽取，所以同一個 seed 的建築形狀與材質都和以前一樣，而且一樣可以重現（LVL-2）。
- 碎塊改回使用建築的漆色。
- 「材質牆」測試場景的每道牆分成四條不同漆色，用來確認換了顏色以後材質仍然認得出來。

**驗證方式**：把截圖轉成灰階，確認五種材質靠紋理仍然分得出來。最終仍以使用者在手機上試玩為準（ACC-1）。

**試玩調整（2026-10-18）**：依使用者回饋，玻璃的色盤和貼圖調亮，鐵的色盤調暗並降低飽和度，貼圖改成素色鐵板加細深色邊框與四角鉚釘（拿掉浪板紋路）；石頭從兩排規矩的大石塊改成大小不一的亂石；石頭的每一格再依座標隨機轉 90° 的倍數（instance 矩陣，不改 shader、沒有效能成本；不用鏡像，因為負縮放會讓面的正反顛倒），避免大面牆看出重複的圖樣。木頭和磚有上下方向，不轉；木紋改成直向，色盤裡的藍色換成深木色；磚改成長方形，並加大每塊磚的深淺差異。

**已知取捨**：玩家不能再只靠顏色判斷材質，例如藍色烤漆鐵和藍色玻璃，要靠紋理和光澤分辨。鐵沒有紋路，主要靠素面、邊框、四角鉚釘和高光辨識；離得很遠、鉚釘看不清時，會比較接近一般的素色方塊。遠處的磚紋會糊成細雜訊，但仍然和其他四種不同。

## ADR-021：音效用 Web Audio 即時合成，並在事件與播放之間加一層防噪音規則

- 狀態：採用
- 日期：2026-10-18
- 相關 spec：AUD-1 ~ AUD-9、VIS-1、PLT-3

**背景**：spec v0.5 加入音效。物理模擬已經會產生 `bounce` 和 `destroy` 事件，帶著撞擊速度與材質，所以不需要改物理。要決定的是聲音從哪裡來、怎麼避免一次撞擊或連續小彈跳變成噪音，以及手機的限制。

**選項**：
- (a) 音檔（取樣）：比較擬真，但要找素材、處理授權，下載量增加，調整要換檔案。
- (b) Web Audio 即時合成：零素材、零下載，參數可以在 `?debug` 現場調；聲音比較粗糙。
- (c) 引入音效函式庫（例如 Howler、Tone.js）：功能比需要的多，仍然要決定 (a) 或 (b)。

**決定**：採用 (b)。
- 粗糙、不擬真的聲音正好符合 AUD-7 與 VIS-1。不同材質用不同的音調、雜訊濾波與衰減長度區分（AUD-2）。
- 分三層，前兩層是純邏輯、可以測試：`soundCues.ts`（事件 → 提示、合併、冷卻、音量）、`recipes.ts`（提示 → 配方資料）、`soundPlayer.ts`（配方 → Web Audio 節點）。
- 防噪音（AUD-8）放在提示層：同一個 frame 合併、有破壞時吞掉同時的建築撞擊聲、同一種聲音的冷卻時間、同時發聲上限，最後加 limiter。
- 音量隨距離衰減（AUD-4）只看「鏡頭到球」的距離，不做立體聲定位：所有聲音都在球的位置，相機通常也朝著球。
- AUD-9：設定 `navigator.audioSession.type = 'ambient'`，讓 iOS 的靜音開關生效。

**效能**：混音在瀏覽器的音訊執行緒進行。主執行緒每個提示只建立幾個短命的節點（最多的破壞音約 15 層），播完自動回收。每次撞擊（不是每個方塊）最多一個提示，再加上冷卻與發聲上限，所以大範圍破壞不會產生大量節點。下載量不變（沒有音檔，程式碼約 10 KB）。

**已知取捨**：
- 合成的聲音不擬真，品質取決於配方的調整，需要靠試玩反覆修改。
- Android 網頁無法得知手機是否在靜音模式，只能靠媒體音量或遊戲內的靜音按鈕（見 README「已知限制」）。

## ADR-022：看不到球時，用 shader 在相機到球之間挖出網點透視通道

- 狀態：採用
- 日期：2026-10-18
- 相關 spec：CAM-3、CAM-2、VIS-1

**背景**：擊球模式的相機被建築擋住時會往上抬（ADR-017）。如果怎麼抬都看不到球（例如球在打出來的隧道裡），原本只有球、瞄準箭頭和預覽以透視方式畫在建築前面，玩家看不到球周圍和前方。CAM-3 要求擊球模式下，擋在相機與球之間的建築以半透明顯示。建築是依材質分成 5 個 `InstancedMesh`，每個露出來的方塊是一個 instance，沒有「一棟一個 mesh」。

**選項**：
- (a) Shader 通道：fragment shader 計算像素到「相機→球」線段的距離，通道半徑內的像素用 4×4 Bayer 網點丟棄一部分。
- (b) 整棟建築 alpha 半透明：每幀找出擋路的建築，給 instance 一個透明度屬性並開啟 `transparent`。
- (c) 整棟建築網點：選法同 (b)，畫法同 (a)。

**決定**：採用 (a)，擊球模式下一律啟用，靈魂出竅模式不啟用。
- 最初只在相機判斷「沒有任何俯角能看到球」時啟用；使用者試玩後改成擊球模式下一律啟用。自動抬高相機（ADR-017）維持不變，所以大多數時候視線本來就是通的，通道只會挖到圓錐邊緣碰到的建築。
- 通道是以球為錐點、相機為錐底的圓錐：半徑在相機端是 `radius`（4 格），沿著相機→球線性縮小到球的位置為 0。最初做的是等寬的圓柱（半徑 2.5 格）；使用者試玩後要求改成圓錐，讓球周圍挖得少、相機周圍挖得多。
- `render/cutaway.ts` 用 `onBeforeCompile` 為每種建築材質產生一份網點版本，共用同一組 uniform（相機位置、球的位置、半徑、挖空比例）。
- 只挖「水平方向上比球更靠近相機至少 `margin`（0.5 格）」的部分；球旁邊和球前方（擊球方向）的建築一律不挖。最初的版本用的是「投影到相機→球線段上 0 < h < 1」，但靠球那端的切面垂直於視線，相機往下俯視時會往前傾，最多挖到球前方約 2.3 格，球旁邊 2.5 格內的牆也會被挖，讓玩家從側面看穿到更遠的建築；試玩時被使用者發現後改成現在的條件。`cutawayWeight()` 是 shader 判斷的 TypeScript 版本，用來測試這個幾何條件，兩邊要保持一致。
- 每幀在 CPU 檢查圓錐內有沒有建築（`coneHitsSolid`）：沿著軸線每半格取一個圓盤，圓盤上的環與點大約間隔一格，只取 shader 會挖的位置，碰到建築就提早結束。只有擊球模式而且圓錐內有建築時才啟用；視線通暢時建築維持一般材質。量測（桌機 Node）：相機距離 14 格時約 750 個取樣、0.03 ms；最遠的 80 格時約 4300 個取樣、0.09 ms。取樣間隔約一格，可能漏掉只擦到圓錐邊緣的單一方塊；那裡本來就在漸淡區，只挖一點點，影響不大。
- 強度依 `fadeRate` 指數淡入淡出，接近終點時直接設成 0 或 1。強度大於 0 時才把建築換成網點材質，回到 0 就換回原本的材質。
- 啟動時先把網點材質換上去呼叫一次 `renderer.compile`，再換回來，避免第一次觸發時編譯 shader 造成卡頓。
- 新增開發者測試場景 `tunnel`，用來確認效果。

**理由**：
- 每一層都用同一個螢幕網點，所以多層牆疊在一起時，被挖掉的像素在每一層都是同一批，會直接看穿整段通道。真正的 alpha 會一層一層變暗，而且 instance 之間不排序，會有前後錯亂。
- 不用改 mesh、不用每幀重建 instance；CPU 每幀只更新幾個 uniform。
- 只挖擋路的那一段，周圍的城市照常顯示。(b)、(c) 遇到互相重疊的大建築（ADR-016）可能會讓一大片城市消失。

**效能**：啟用時每個建築像素多大約 20 個運算，可以忽略。`discard` 會讓部分手機 GPU 失去 early-Z 最佳化，所以只在圓錐內真的有建築時才換上網點材質（曾經改成擊球模式下一律換上，後來為了手機效能改成現在的做法；畫面效果相同，因為圓錐內沒有建築時本來就沒有東西可挖）。陰影用的是另一個 depth material，被挖掉的方塊照樣投影。

**已知取捨**：被挖開的牆沒有封面，可以看到建築裡面是空心的（只畫露在外面的方塊）。網點的顆粒感符合 VIS-1 的粗糙風格。

## ADR-023：靈魂出竅在進入時扣款，分數不足時停用按鈕

- 日期：2026-10-18
- 相關 spec：CAM-4、DES-7

**背景**：CAM-4 要求每次進入靈魂出竅花費「已使用次數 × 50」破壞分數，且分數不能變成負數。

**選項**：(a) 分數不足時按鈕照樣可按，按下後跳提示說明不夠；(b) 分數不足時直接停用按鈕。

**決定**：採用 (b)。按鈕上本來就顯示費用，旁邊也顯示目前分數，停用狀態已足以說明原因，不需要額外提示。扣款在進入時發生，回到球不退費；使用次數在每一關（重玩、新地圖）重新計算，因為 `Game` 每關重新建立。每次的費用單位放在 `config.soul.costPerUse`，方便試玩後調整。
